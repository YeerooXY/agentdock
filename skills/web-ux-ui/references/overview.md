# Website design workflow

Use the user's brief, existing brand and current product facts. Record audience, entry route, immediate task, main action, evidence, constraints and success condition. Infer known facts from the project; ask only when a missing fact changes the work.

## Start from an ordinary website request

Apply this workflow when the user asks to create a website, without requiring them to name a guide, skill or reference site. Read content for the CTA playbook, then layout, visual, verification and checklist as needed. Preserve the user's chosen tools and project. A request for a repair does not authorize a redesign.

1. **Brief.** Establish the business/product name, offer, audience, primary visitor action, contact or download destination, existing assets and constraints. Read known facts from the project. Ask only for missing facts that affect the work. Keep unknown prices, business identity and operational claims out of published copy.
2. **References.** Select two or three examples relevant to the task from the content playbook and source register. Inspect the dated evidence or the current pages. Record the pattern to adapt, its purpose and its limits. Use an actual product screenshot when the product exists. An attractive competitor page does not establish conversion gains.
3. **Direction.** Read creative for an open visual brief. Draft three structurally different composition ideas from the same facts and primary action, then render the comparison in one flat 2D image when practical. The creative role supplies spatial relationships and image prompts; the image generator renders them. Save the concept and let the owner select a direction before a substantial build. An already specified direction can proceed. In an explicitly unattended benchmark, use its predeclared selection rule and record who selected. For an existing ambiguous screen, inspect its actual screenshot and follow the Screen previews setting. If generation is unavailable, offer an editable local layout proposal and name the limitation; do not call a screenshot an AI concept.
4. **Assets.** Generate the site's own images when useful and supported by the selected tools. Record sources, permissions and required attribution for supplied or licensed assets. Reference captures are internal study material and must not become the site's images or copied prose. Generating a realistic product photograph does not make it evidence of a real product.
5. **Build.** Implement the selected composition and complete primary journey, including waiting, empty, error and success states. Use the playbook for the actual site type. Each visible action needs a destination or implemented outcome. A contact form must not claim delivery without a working receiver. A download must identify the correct platform and actual artifact.
6. **Verify and revise.** Run project checks; inspect the rendered journey on the four platform profiles described in verification. Complete the applicable 20 page and 50 security items with evidence. Obtain an independent code/design review when the task uses orchestration. Fix confirmed findings and rerun affected checks on the final revision. Keep host-only checks open until that host is tested.
7. **Handover.** Save requested outputs, useful design decisions and the review note. Report the real state of the primary journey, tested revision, emulated coverage and remaining owner/deployment facts. Publish only within the user's authorization.

## Orchestration handoff

The lead agent owns factual intake, reference choice, the owner's direction decision and integration. Keep one lead by default. Add a worker only for a bounded outcome that benefits from its capabilities; identify files, dependencies and acceptance checks. Carry the relevant facts, selected direction and asset paths into that handoff. Workers receive the compact worker contract; planners also receive creative, and the first reviewer receives the checklist. Full reference topics stay available on demand.

When local assistance is available, assign one concrete output through dock/local_assist (for example, three composition proposals from the real brief, a copy critique, or one isolated component). Verify and use the useful result. Record adoption or rejection and the reason; a local call that is discarded and repeated in the cloud has not established savings. Prefer deterministic scripts for link, encoding, layout and test checks. A stopped local server is a capability gap; do not silently replace it with a paid request.

Use configured accounts and routing. Paddock's task loop already runs implementation, checks, review and retries; an outer queue should not add a duplicate REVIEW step. For a new bounded delegation, use one build and one targeted correction as the initial allowance (maxRounds: 2); diagnose scope, capability or model fit before authorizing more work. This is a working default, not a proven optimum. A passed command alone is insufficient: inspect final checks and review evidence against the same revision. Carry current unresolved findings into a fix or escalation. A question, unavailable capability or exhausted attempt budget remains visible; do not silently mark it done.

Before dispatch, put known generated outputs (build files, screenshots, Python caches, test logs) in project-specific ignored directories. Keep real source files under review. Checks must not rewrite source silently; a source change makes their evidence stale and requires another run. Do not disable stale-evidence detection to get a green task.

Check actual worker capabilities before assigning image generation or browser work. A worker without those tools returns its asset or verification request to the orchestrator. OpenCode text output is not an image, and selecting agent mode in an image tool does not remotely invoke another agent. Use an available image-capable agent or configured generator according to the owner's settings; record tool unavailability before choosing a fallback.

## Route by task

| Experience | First useful decision | Read next |
| --- | --- | --- |
| Software or service marketing | Understand the offer and choose a suitable next step | layout, content, visual |
| Portfolio or editorial | Identify author/topic and inspect relevant work | layout, content |
| Shop, catalogue, product or checkout | Find, compare and buy the correct item | commerce, visual, content |
| Booking or lead form | Understand eligibility, availability, cost and commitment | layout, content, verification |
| Application or dashboard | Continue work, understand status and recover from failure | layout, visual, verification |

All implemented pages need verification. Read only the topics relevant to the task. A small button repair does not require a full redesign.

## Deliver a working experience

1. Inspect the current implementation and relevant real references. Name the pattern and why it fits. A shipped competitor pattern is a hypothesis for our audience, not proof of effectiveness.
2. Define content order and the complete primary journey, including empty, waiting, error and success states. For substantial ambiguous redesigns, follow the user's Screen previews setting.
3. Set a small system of semantic color roles, type, spacing, media treatment and interaction rules. Preserve brand choices that serve the task.
4. Build the authorized result. Give every visible control a real outcome. Keep unsupported claims, invented reviews and fake operational activity out of the page.
5. Verify the rendered primary journey across desktop, mobile and tablet. Complete the applicable page and security reviews from the shared web-design guide. Fix concrete defects.
6. Save requested deliverables with their useful design decisions and selected evidence. State what was tested and what remains unknown.

## Evidence labels

Distinguish standards, research findings, platform guidance, live observations, working defaults and hypotheses. Screenshots establish visible composition; they do not establish task success, speed, conversion or conformance. A clean automated scan is one form of evidence.
