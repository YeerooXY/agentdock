# Cross-module migration trial

The documented condition showed no coding advantage in this paired trial. Both
conditions passed all 12 migration checks on their first attempt. The extra
knowledge-map upkeep used more tokens and was not accepted after review.

This is one pair on Nemosite, not evidence that documentation never helps.
Smaller models and larger codebases remain untested.

## Work performed

Two fresh native Sonnet 5.5 chains planned and implemented the same migration in
isolated copies. Both changed the generator, image-preparation script, Worker
import, README and ignore rules; moved six groups of input files; and retired
the old generated Worker module. Package/deployment entrypoints stayed intact.

Source-only used ordinary source tools and no optional application map. The
documented condition retrieved the compact index and relevant original canonical
notes before planning. Implementation reused that plan and the index. Its
knowledge map was maintained in a separate phase after code verification.
Both conditions updated the normal README as part of the migration.

The fixture had 3,634 common input files, mostly small synthetic image stand-ins.
It used real application modules, content and dimension metadata, with sanitized
deployment configuration. No actual private photographs were copied. The
unchanged fixture generated 107 pages and passed checks for 8,403 local link/image
references. This was a broader change in a relatively small codebase, not a large
application benchmark.

## Acceptance and execution

Before model calls, a reference migration passed the checker and unchanged code
failed it. The checks accepted different source/output directory designs rather
than requiring the reference implementation's paths.

Both implementations passed:

- Confined file operations and preservation of opaque input/private-asset bytes.
- Build from missing output, with common writes to tracked source prohibited.
- The original page, CSP and link checks.
- Exclusion of held images and retired routes from public output.
- Removal of stale output and identical output bytes on a repeated build.
- Unchanged source tree and ignored generated output.
- Correct Worker import and regenerated project data after a source-content edit.
- Offline build from a reconstructed checkout of tracked source.
- All 18 original mocked endpoint tests.
- Manual image preparation writing outside output, using an empty manifest and
  stub PIL. Real decoding and external archives were not tested.

There were five native attempts: two planners, two implementers and one updater.
Neither condition needed its optional code-repair attempt. All used the same
included Claude account, effective `claude-sonnet-5-5`, medium effort, with an
8,192-token output cap. There were zero output-limit continuations and zero
native tool errors. All plan artifacts were valid JSON files; terminal chat was
kept short. The earlier output-limit problem did not recur.

Agents had Read/Grep/Glob/Write/Edit only. The host applied confined declared
copy/removal operations and ran offline checks. Network/subprocess calls were
blocked in Node build probes. Native initialization reported no MCP servers or
automatically discovered skills. No Paddock task wrapper, deployment, live email,
dependency install, provider fallback or live Nemosite edit was used.

## Upkeep review

The updater changed three existing sections, preserved IDs and left code alone.
It accurately recorded important new paths and the fixture-only scope. It also
reported unresolved documentation issues. Direct source/reference review found:

- Two Markdown source links still point to removed `worker/projects.mjs`,
  including one inside the generation section it had just updated.
- A new overview sentence says `held-project-assets` is read. The migrated
  generator does not read that directory; it leaves it untouched.
- An unqualified retained paragraph says the build was not exercised, while
  the new fixture description reports host builds. Historical verification needs
  an explicit scope label.

Upkeep is therefore **partial and unaccepted**. No additional model call or
silent coordinator repair hid its cost or changed this outcome. Matching source
paths or passing code tests would not establish semantic documentation accuracy.
A deterministic reference audit can catch the missing links without inference;
the behavioral claims still need source review.

## Interpretation and limits

For this Sonnet task, reading notes did not avoid a repair or improve the tested
coding result. Planning/implementation usage was close; map upkeep added work
and left drift. This case does not justify automatic prose upkeep by itself.
Keep it optional while evaluating specific benefits.

The treatment deliberately required relevant-note retrieval. The tested surface
was a frozen file-based projection of the new context engine, not a live Paddock
endpoint. The task's acceptance criteria already stated important private-asset
obligations. Documentation containing unique owner intent, or retrieval helping
a smaller worker, could behave differently. There was only one run per condition.

No real browser rendering, image decoding, Cloudflare bundle, deployment or live
email was verified. The trial implementations remain temporary experimental
artifacts and have not been approved for the live project.

Raw prompts, fixture hashes, checker admission, traces, phase usage, code checks
and maintenance review are in `.build/cross-module-native-2026-11-06/`.
`verification.json` separates code success from unaccepted upkeep.

Unrelated wording finding: the frozen `scripts/build-pages.mjs` page-title
template contains a decorative em dash in the Nemozoli engineering title. It
was flagged and preserved for input equality; no live copy was rewritten.
