# Repository tasks

Open **Tasks**, select a project folder or an open local console folder, and enter a title and acceptance criteria. The folder must be the Git repository root; subfolders are rejected to keep the implementer’s write scope explicit. Pick the implementer account and an independent reviewer account, or **No review**. Model fields accept model identifiers. Reviewer suggestions show the reason; assignments stay fixed for the task.

Paddock runs implementation, your checks command, and a read-only review. Failed check output and confirmed review findings go into the next implementation prompt. A review requesting changes with unstructured findings passes a redacted answer tail to the next round. Only the user can set the checks command. The implementer’s summary cannot pass a task.

- **Current branch** edits the working copy. Paddock records HEAD, a `git stash create` snapshot (HEAD when clean), and hashes of existing untracked files. Unchanged files stay excluded. Modified or deleted untracked files appear in prompts, reviews, the diff stat and report with baseline hashes; modified files include a current-content preview. Original untracked contents are not stored, so those entries describe the change rather than provide a reconstructable patch. Private/generated files use size and modification time; their contents stay excluded. The index and working files are preserved.
- **Separate worktree** creates `<data>/task-worktrees/<id>` on `paddock/task-<id8>` from HEAD. It excludes the source working copy’s uncommitted work. Paddock keeps the worktree and branch for manual cleanup.

Claude Code, Codex and Kiro use the same installed-account list and account environment wiring as cross-agent reviews. Paddock never reads or forwards sign-in tokens. A CLI sign-in failure is reported separately from an unsuccessful solution. The selected vendor receives the task; the reviewer receives its criteria and changes. Private and generated paths are excluded from reviews and reports.

Tasks use 1–5 rounds (default 3), 5–120 minutes (default 30), one running task per Git repository, and two running tasks total. Checks run in the platform shell with a 15-minute timeout and an 8,000-character output tail. On Windows the wrapper uses UTF-16LE `-EncodedCommand` to preserve quotes and Unicode, and process-only `-ExecutionPolicy Bypass` so npm’s PowerShell shim can run. System policy is preserved. Handoffs contain at most 4,000 characters of previous failed checks. Provider processes receive prompts on stdin. Implementation permits file edits; reviews use the existing read-only launcher.

`implementing`, `checking` and `reviewing` identify the current step. `passed` requires successful checks and reviewer approval, with omitted steps treated as not set. `needs-you` covers findings, failed checks (including a checks command that cannot start), stale verification, repository/diff errors and exhausted limits. `failed` identifies provider errors, including a provider process that cannot start. Stop kills the process tree and waits for its close event for up to two seconds before capturing the diff and report. A timeout leaves a visible warning. Work is preserved. Quit kills and persists active tasks as `interrupted` synchronously, with diff/report recovery deferred to startup. Persisted active tasks also become `interrupted` at startup and never resume automatically. Accept records `accepted`; it does not commit or merge.

Tasks are saved in `<data>/tasks/<id>.json`. Automatic refresh handles at most two `passed`/`needs-you` tasks per cycle, at intervals of at least five seconds per task. It fingerprints the baseline diff and untracked paths and contents. File hashes are cached by size, modification time and change time; unchanged files are not read again for hashing. Disappearing files are skipped. Temporary read, lock and Git timeout errors preserve the last verification and retry on the next cycle; Accept asks for a retry if its refresh fails. Missing baselines and oversized diffs stop further automatic refresh and require inspection. Verification also expires after seven days, before the temporary unreferenced Git baseline normally ages out; its saved diff stays available. Accepted, stopped, failed and recovered interrupted tasks keep their saved diffs and reports unchanged. The page publishes the 20 latest completed tasks plus running tasks; older reports stay in Results. Published progress is capped at 8,000 characters per running task; baseline file lists and hashes stay in main-process storage. Codex and Claude usage events provide token counts; Kiro summaries use a redacted stdout tail. Missing usage stays **not reported**. No quota percentages or costs are inferred.

The Tasks detail shows round timelines, output tails, findings, elapsed time, usage and the diff. Status changes update a persistent polite live region while keyboard focus stays on the selected control. **Open report** opens a Markdown report in Results, including the final diff capped at 60 KB. Reports update while awaiting acceptance and record the final acceptance. Large diffs stop as `needs-you` for manual review.

IPC methods are `tasks.start`, `tasks.stop`, `tasks.accept`, `tasks.list` and `tasks.candidates`. Only the trusted main renderer exposes them; agent tools cannot start tasks or alter their commands. The published state includes `tasks`. Task diff reads disable fsmonitor and text conversion drivers; report metadata reads disable fsmonitor.

`tests/task-loop.test.cjs` uses temporary Git repositories and mocked provider/check processes. `scripts/task-loop-smoke.cjs` is in the desktop suite and checks keyboard operation, live-region persistence, focus, the 984 px layout and Results. Desktop fixtures use saved tasks and simulated state updates; providers are disabled. These checks do not replace a manual screen-reader session. Run the build, unit tests and Docker desktop tests where those commands are allowed.
