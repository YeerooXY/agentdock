# Current task disposition, 5 November 2026

Start delegated work through `dock/start_task`. New tasks use the automatic-resolution setting; older saved jobs retain their
manual policy. Completion rechecks the current diff fingerprint, HEAD, configured
checks and reviewer findings. System resolution records its actor and evidence.
A task with no checks is explicitly completed-unverified, not verified.

Current-checkout resolution never merges. Isolated worktree publication uses the
existing guarded merge-back path and requires checks. A durable prepared record
precedes publication; uncertain crash recovery requires inspection and never
replays publication automatically. Documentation failures after publication keep
a pending outbox without relabelling successfully published code as failed.

Five agent slots are admitted per project. Unspecified cloud-account caps no
longer impose a one-job default; explicit caps, fresh allowance gates, local
serialization and exclusive current-checkout editing still apply. Five slots do
not authorize five concurrent writers in one checkout.

The owner requested 20-minute bounded implementation slices and 8-minute focused
reviews. These are dispatch choices. The general task default remains 30 minutes.

The following describes advanced/manual task workflows retained for compatibility.

# Repository tasks

Ask an agent console to run a task. The agent calls `dock/start_task` with `title`, `criteria`, an `implementer` account (`accountId`, optional `model` and provider-supported `effort`), and an optional independent `reviewer` account. `repo` defaults to that console's folder; it must be the Git repository root. Optional fields are `checks`, `workflow`, `maxRounds`, `timeLimitMinutes`, `split` and `planner`. Split tasks can use configured routing defaults. Use `dock/task_candidates` with `refresh:true` for fresh quota and model discovery, then `accountId` for the account model list and supported efforts. Antigravity reads its native `models` catalog under the same account-switch lease as quota; model discovery failure preserves quota and reports a separate message. Claude reuses the model catalog from usage initialization. Medium and large suggestions require a fresh suitable model; an unsuitable configured reviewer produces an eligible discovered reviewer suggestion and a warning; explicit task assignments retain their selected route. The tool returns the task ID. **Tasks** shows live progress, checks, reviews and results, with controls to approve a plan, stop, resume or accept work.

Paddock runs implementation, your checks command, and a read-only review. Failed check output and confirmed review findings go into the next implementation prompt. A review requesting changes with unstructured findings passes a redacted answer tail to the next round. The checks command comes from the task request. The implementer’s summary cannot pass a task.

- **Current branch** edits the working copy. Paddock records HEAD, a `git stash create` snapshot (HEAD when clean), and hashes of existing untracked files. Unchanged files stay excluded. Modified or deleted untracked files appear in prompts, reviews, the diff stat and report with baseline hashes; modified files include a current-content preview. Original untracked contents are not stored, so those entries describe the change rather than provide a reconstructable patch. Private/generated files use size and modification time; their contents stay excluded. The index and working files are preserved.
- **Separate worktree** creates `<data>/task-worktrees/<id>` on `paddock/task-<id8>` from HEAD. It excludes the source working copy’s uncommitted work. Paddock keeps the worktree and branch for manual cleanup.

Claude Code, Codex and Kiro use the same installed-account list and account environment wiring as cross-agent reviews. OpenCode uses its installed CLI and requires an OpenCode Go or free model ID. Its prompt and role-specific permission config are stored temporarily in Paddock's data folder. Paddock never reads or forwards sign-in tokens. A CLI sign-in failure is reported separately from an unsuccessful solution. The selected vendor receives the task; the reviewer receives its criteria and changes. Private and generated paths are excluded from reviews and reports.

Tasks use 1–5 rounds (default 3), 5–120 minutes (default 30), one running task per Git repository, and two running tasks total. Checks run in the platform shell with a 15-minute timeout and an 8,000-character output tail. On Windows the wrapper uses UTF-16LE `-EncodedCommand` to preserve quotes and Unicode, and process-only `-ExecutionPolicy Bypass` so npm’s PowerShell shim can run. System policy is preserved. Handoffs contain at most 4,000 characters of previous failed checks. OpenCode receives a prompt file; other provider processes receive prompts on stdin. Implementation permits file edits; reviews use read-only permissions.

`implementing`, `checking` and `reviewing` identify the current step. `passed` requires successful checks and reviewer approval, with omitted steps treated as not set. `needs-you` covers findings, failed checks (including a checks command that cannot start), stale verification, repository/diff errors and exhausted limits. `failed` identifies provider errors, including a provider process that cannot start. Stop kills the process tree and waits for its close event for up to two seconds before capturing the diff and report. A timeout leaves a visible warning. Work is preserved. Quit kills and persists active tasks as `interrupted` synchronously, with diff/report recovery deferred to startup. Persisted active tasks also become `interrupted` at startup and never resume automatically. Legacy manual Accept records `accepted`; it does not commit or merge.

Tasks are saved in `<data>/tasks/<id>.json`. Automatic refresh handles at most two `passed`/`needs-you` tasks per cycle, at intervals of at least five seconds per task. It fingerprints the baseline diff and untracked paths and contents. File hashes are cached by size, modification time and change time; unchanged files are not read again for hashing. Disappearing files are skipped. Temporary read, lock and Git timeout errors preserve the last verification and retry on the next cycle; Accept asks for a retry if its refresh fails. Missing baselines and oversized diffs stop further automatic refresh and require inspection. Verification also expires after seven days, before the temporary unreferenced Git baseline normally ages out; its saved diff stays available. Accepted, stopped, failed and recovered interrupted tasks keep their saved diffs and reports unchanged. The page publishes the 20 latest completed tasks plus running tasks; technical reports stay in internal execution history. Existing saved Results retain their files and IDs. Published progress is capped at 8,000 characters per running task; baseline file lists and hashes stay in main-process storage. Codex and Claude usage events provide token counts; Kiro summaries use a redacted stdout tail. Missing usage stays **not reported**. No quota percentages or costs are inferred.

The Tasks detail shows round timelines, output tails, findings, elapsed time, usage and the diff. Status changes update a persistent polite live region while keyboard focus stays on the selected control. Current structured outcomes come directly from task state; older snapshots can still use a linked saved Result. Routine task and review reports are stored under `<data>/execution-history/` with stable task/review IDs and content revisions. They do not create Results cards. **Open report** reads internal reports in a plain-text dialog; legacy links still open historical saved reports. The shared task/review status tools accept `includeReport`, `reportOffset`, `reportLimit` (up to 64,000 characters) and `reportRevision` for bounded, revision-pinned reads. Task reads retain the repository guard; review reads retain caller-console ownership. Internal records update while awaiting acceptance and record the final acceptance. Large diffs stop as `needs-you` for manual review.

IPC methods are `tasks.start`, `tasks.stop`, `tasks.accept`, `tasks.list` and `tasks.candidates`. Only the trusted main renderer exposes them; agent tools cannot start tasks or alter their commands. The published state includes `tasks`. Task diff reads disable fsmonitor and text conversion drivers; report metadata reads disable fsmonitor.

## Owner activity and retained history

Completed tasks remain available for reports, explicit status reads and recovery. The Tasks snapshot publishes running tasks and at most 20 completed tasks; the main-process job map currently retains older records too. Dismissing a task hides it without deleting its execution history. Archive loading is not yet lazy, so the displayed-history limit is not a memory-retention limit.

Repeated typing that changes only the exact activity timestamp no longer emits the owner registry's synchronous `changed` event. It uses the existing two-second persistence batch, avoiding scheduler drain and retained-job reconciliation on those keys. Ownership, focus replacement, demand flags and reservations still use the immediate durable path. If a critical save fails, the next interaction retries that path immediately. This removes history scans from ordinary typing without deleting reports or weakening owner protection.

## Split tasks

Ask the agent to use `split: true` to create a read-only plan before building. The planner defaults to the large-task routing choice. A plan contains shared contracts and 2–8 subtasks with criteria, owned file globs, dependencies and sizes. Paddock validates paths, cycles and overlapping ownership, allows one validation repair, and runs at most two plan review rounds. **No review** displays **Plan not reviewed**. The states are `planning`, `reviewing-plan` and `plan-ready`.

At `plan-ready`, review contracts, findings and assignments. Routing spreads assignments across accounts within 10 points of the best measured usage; unknown or stale usage never counts as free capacity. Change each account/model, choose the main implementer for integration fixes and set 1–4 simultaneous subtasks (default 2). **Approve plan** starts building. **Stop** keeps all branches and worktrees. Nothing builds before approval.

Split tasks always use a separate integration worktree at `<data>/task-worktrees/<id>` on `paddock/task-<id8>`. Each subtask uses `<id>-<sub>` on `paddock/task-<id8>-<sub>`, created from the integration HEAD when it starts. Dependencies must be merged first. Subtasks run the existing implement/check/review/fix loop with their contracts and ownership. Changes outside ownership become fix findings and block a pass. Changing contracts requires stopping. Paddock commits passing subtasks using the repository identity (fallback `Paddock <paddock@localhost>`) and merges them into the integration branch with `--no-ff`. Conflicts are aborted and listed as `needs-you`. Four provider processes may run across all tasks; the repository and task concurrency limits still apply.

After building, checks and the final review cover the combined diff, contracts and plan. Findings go to the main implementer using the remaining integration rounds and active time budget; waiting for approval does not consume that budget. Checks and reviews record integration HEAD as well as the diff fingerprint. Later HEAD or file changes make verification out of date. **Accept** records acceptance without merging into your branch.

Startup marks active subtasks `interrupted` and never starts them automatically. **Resume** is available for stopped, interrupted and `needs-you` split tasks. It skips merged subtasks and reuses other worktrees with previous findings and another subtask round allowance. Integration rounds and the task time limit remain bounded. Resume refuses to start while a previous process is still active. An unapproved saved plan returns to approval. Reports include contracts, assignments and reasons, subtask rounds and outcomes, and reported usage per subtask and account. Missing usage remains **not reported**; quota percentages and costs are never inferred. The trusted-renderer IPC adds `tasks.approvePlan` (id, assignments keyed by subtask id, optional main implementer and parallel limit) and `tasks.resume` (id); agent tools expose neither method.

`tests/task-loop.test.cjs` uses temporary Git repositories and mocked provider/check processes. `scripts/task-loop-smoke.cjs` is in the desktop suite and checks keyboard operation, live-region persistence, focus, the 984 px layout and Results. Desktop fixtures use saved tasks and simulated state updates; providers are disabled. These checks do not replace a manual screen-reader session. Run the build, unit tests and Docker desktop tests where those commands are allowed.


## Interface reviews and worker verification

`dock/website_guide` keeps its existing tool name. New user-facing interfaces use overview and the relevant topic: app for desktop/Electron/mobile apps, game menus, dashboards and internal tools; content for website offers and calls to action. New visual directions use three distinct compositions and the owner's selected concept. Small repairs preserve the existing screen and scope.

`dock/review_page` accepts HTTP(S) URLs, including local development servers. It runs Chromium desktop, WebKit desktop, Android Chrome and iPhone WebKit emulation. Browser engines ship with the prepared runtime. Each profile reports complete or not-run; missing profiles count as findings. Physical devices and native-shell behavior still require separate verification. The unstyled hints identify default serif body text, native controls, default links, an 8px body margin and missing theme color variables. These are review hints, with intentional editorial or native styling considered in context. Local files should be served through the project's dev server; file URLs remain blocked.

Builders receive the configured checks command. Claude, Antigravity and OpenCode receive a native permission allowance for a literal command; native matching and owner policy still apply. Pi receives a fixed `run_checks` tool with no command or folder argument. Codex retains workspace-sandbox execution. Other adapters retain their existing command restrictions. Reviewers and Knowledge maintenance receive no new execution permission. Commands containing quoting, shell operators or permission-pattern characters stay in the host verification phase. Workers report unavailable execution and actual test results. Paddock independently reruns final checks and preserves stale-evidence detection.

`task_status.usageSummary.lead` reports recorded origin-console turns that overlap the task window, including input, output and cached input. `totalCloud` adds these measurements to worker totals. Turn IDs are deduplicated within a task. A turn shared across tasks must be deduplicated again when comparing a group of tasks. Planning before the window and integration afterward are excluded, and active turns may arrive after completion. Missing measurements remain unavailable. This partial attribution keeps `cloudComplete:false`; a full benchmark must account for the remaining work.

Native permission references: [Antigravity](https://antigravity.google/docs/permissions), [Claude Code](https://code.claude.com/docs/en/permissions), [OpenCode](https://opencode.ai/docs/permissions/). Installed OpenCode adapters currently use the V1 permission shape; V2 uses different field names and requires an adapter update before use.

Review issue totals count unique rules or broken URLs across profiles. `report.issueSummary` lists category totals, each finding and affected profiles. Visible typography is inventoried per profile; more than 3 font stacks, 8 sizes or 5 weights prompts a review hint. Existing saved review findings are regrouped on load; typography measurement requires a new capture.

Automatic builder suggestions prefer a newer fresh discovered release within the same model family and capability tier when candidates have comparable allowance, after assigned-work balancing. Native Antigravity quota readings identify an included allocation; worker credit spending remains disabled.
