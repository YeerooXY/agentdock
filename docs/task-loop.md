# Repository tasks

Ask an agent console to run a task. The agent calls `dock/start_task` with `title`, `criteria`, an `implementer` account (`accountId`, optional `model` and Codex `effort`), and an optional independent `reviewer` account. `repo` defaults to that console's folder; it must be the Git repository root. Optional fields are `checks`, `workflow`, `maxRounds`, `timeLimitMinutes`, `split` and `planner`. Split tasks can use configured routing defaults. The tool returns the task ID. **Tasks** shows live progress, checks, reviews and results, with controls to approve a plan, stop, resume or accept work.

Paddock runs implementation, your checks command, and a read-only review. Failed check output and confirmed review findings go into the next implementation prompt. A review requesting changes with unstructured findings passes a redacted answer tail to the next round. The checks command comes from the task request. The implementer’s summary cannot pass a task.

- **Current branch** edits the working copy. Paddock records HEAD, a `git stash create` snapshot (HEAD when clean), and hashes of existing untracked files. Unchanged files stay excluded. Modified or deleted untracked files appear in prompts, reviews, the diff stat and report with baseline hashes; modified files include a current-content preview. Original untracked contents are not stored, so those entries describe the change rather than provide a reconstructable patch. Private/generated files use size and modification time; their contents stay excluded. The index and working files are preserved.
- **Separate worktree** creates `<data>/task-worktrees/<id>` on `paddock/task-<id8>` from HEAD. It excludes the source working copy’s uncommitted work. Paddock keeps the worktree and branch for manual cleanup.

Claude Code, Codex and Kiro use the same installed-account list and account environment wiring as cross-agent reviews. OpenCode uses its installed CLI and requires an OpenCode Go or free model ID. Its prompt and role-specific permission config are stored temporarily in Paddock's data folder. Paddock never reads or forwards sign-in tokens. A CLI sign-in failure is reported separately from an unsuccessful solution. The selected vendor receives the task; the reviewer receives its criteria and changes. Private and generated paths are excluded from reviews and reports.

Tasks use 1–5 rounds (default 3), 5–120 minutes (default 30), one running task per Git repository, and two running tasks total. Checks run in the platform shell with a 15-minute timeout and an 8,000-character output tail. On Windows the wrapper uses UTF-16LE `-EncodedCommand` to preserve quotes and Unicode, and process-only `-ExecutionPolicy Bypass` so npm’s PowerShell shim can run. System policy is preserved. Handoffs contain at most 4,000 characters of previous failed checks. OpenCode receives a prompt file; other provider processes receive prompts on stdin. Implementation permits file edits; reviews use read-only permissions.

`implementing`, `checking` and `reviewing` identify the current step. `passed` requires successful checks and reviewer approval, with omitted steps treated as not set. `needs-you` covers findings, failed checks (including a checks command that cannot start), stale verification, repository/diff errors and exhausted limits. `failed` identifies provider errors, including a provider process that cannot start. Stop kills the process tree and waits for its close event for up to two seconds before capturing the diff and report. A timeout leaves a visible warning. Work is preserved. Quit kills and persists active tasks as `interrupted` synchronously, with diff/report recovery deferred to startup. Persisted active tasks also become `interrupted` at startup and never resume automatically. Accept records `accepted`; it does not commit or merge.

Tasks are saved in `<data>/tasks/<id>.json`. Automatic refresh handles at most two `passed`/`needs-you` tasks per cycle, at intervals of at least five seconds per task. It fingerprints the baseline diff and untracked paths and contents. File hashes are cached by size, modification time and change time; unchanged files are not read again for hashing. Disappearing files are skipped. Temporary read, lock and Git timeout errors preserve the last verification and retry on the next cycle; Accept asks for a retry if its refresh fails. Missing baselines and oversized diffs stop further automatic refresh and require inspection. Verification also expires after seven days, before the temporary unreferenced Git baseline normally ages out; its saved diff stays available. Accepted, stopped, failed and recovered interrupted tasks keep their saved diffs and reports unchanged. The page publishes the 20 latest completed tasks plus running tasks; older reports stay in Results. Published progress is capped at 8,000 characters per running task; baseline file lists and hashes stay in main-process storage. Codex and Claude usage events provide token counts; Kiro summaries use a redacted stdout tail. Missing usage stays **not reported**. No quota percentages or costs are inferred.

The Tasks detail shows round timelines, output tails, findings, elapsed time, usage and the diff. Status changes update a persistent polite live region while keyboard focus stays on the selected control. **Open report** opens a Markdown report in Results, including the final diff capped at 60 KB. Reports update while awaiting acceptance and record the final acceptance. Large diffs stop as `needs-you` for manual review.

IPC methods are `tasks.start`, `tasks.stop`, `tasks.accept`, `tasks.list` and `tasks.candidates`. Only the trusted main renderer exposes them; agent tools cannot start tasks or alter their commands. The published state includes `tasks`. Task diff reads disable fsmonitor and text conversion drivers; report metadata reads disable fsmonitor.

## Split tasks

Ask the agent to use `split: true` to create a read-only plan before building. The planner defaults to the large-task routing choice. A plan contains shared contracts and 2–8 subtasks with criteria, owned file globs, dependencies and sizes. Paddock validates paths, cycles and overlapping ownership, allows one validation repair, and runs at most two plan review rounds. **No review** displays **Plan not reviewed**. The states are `planning`, `reviewing-plan` and `plan-ready`.

At `plan-ready`, review contracts, findings and assignments. Routing spreads assignments across accounts within 10 points of the best measured usage; unknown or stale usage never counts as free capacity. Change each account/model, choose the main implementer for integration fixes and set 1–4 simultaneous subtasks (default 2). **Approve plan** starts building. **Stop** keeps all branches and worktrees. Nothing builds before approval.

Split tasks always use a separate integration worktree at `<data>/task-worktrees/<id>` on `paddock/task-<id8>`. Each subtask uses `<id>-<sub>` on `paddock/task-<id8>-<sub>`, created from the integration HEAD when it starts. Dependencies must be merged first. Subtasks run the existing implement/check/review/fix loop with their contracts and ownership. Changes outside ownership become fix findings and block a pass. Changing contracts requires stopping. Paddock commits passing subtasks using the repository identity (fallback `Paddock <paddock@localhost>`) and merges them into the integration branch with `--no-ff`. Conflicts are aborted and listed as `needs-you`. Four provider processes may run across all tasks; the repository and task concurrency limits still apply.

After building, checks and the final review cover the combined diff, contracts and plan. Findings go to the main implementer using the remaining integration rounds and active time budget; waiting for approval does not consume that budget. Checks and reviews record integration HEAD as well as the diff fingerprint. Later HEAD or file changes make verification out of date. **Accept** records acceptance without merging into your branch.

Startup marks active subtasks `interrupted` and never starts them automatically. **Resume** is available for stopped, interrupted and `needs-you` split tasks. It skips merged subtasks and reuses other worktrees with previous findings and another subtask round allowance. Integration rounds and the task time limit remain bounded. Resume refuses to start while a previous process is still active. An unapproved saved plan returns to approval. Reports include contracts, assignments and reasons, subtask rounds and outcomes, and reported usage per subtask and account. Missing usage remains **not reported**; quota percentages and costs are never inferred. The trusted-renderer IPC adds `tasks.approvePlan` (id, assignments keyed by subtask id, optional main implementer and parallel limit) and `tasks.resume` (id); agent tools expose neither method.

`tests/task-loop.test.cjs` uses temporary Git repositories and mocked provider/check processes. `scripts/task-loop-smoke.cjs` is in the desktop suite and checks keyboard operation, live-region persistence, focus, the 984 px layout and Results. Desktop fixtures use saved tasks and simulated state updates; providers are disabled. These checks do not replace a manual screen-reader session. Run the build, unit tests and Docker desktop tests where those commands are allowed.
