# Autonomous Projects: acceptance contract

Owner correction, 4 November 2026. Future implementation gates, not tests claimed to have run. This replaces the owner-facing task-administration acceptance model. Technical evidence from the earlier contract is retained in .build/plans/tasks-projects-acceptance-before-owner-correction.md.

## Project creation and adoption

1. Greenfield: enter an idea and folder. Produce a provisional component map and first useful increment with reversible defaults. Unimplemented nodes remain proposed. No task-rating form or per-worker approval is required.
2. Existing project: adopt a dirty/untracked repository with owner docs, instructions, multiple applications and stale historical plans. Discovery changes no source/branch/docs and executes no imported scripts. Show evidenced entry points, unknown coverage and the next requested outcome without recreating the project from scratch.
3. Stable identity: correct Agentdock to Paddock as the owner requested while retaining the same ID, bindings, history and searchable alias. Old SSH draft milestones become historical presentation, not completed or deleted items.
4. Planner usefulness: for a seeded feature change, the compact context correctly identifies responsible modules, declared connections, entry points and actual run/check commands with source references. Do not treat a static import as proof of every runtime interaction.

## Knowledge survives sessions

5. Run three separate managed coding sessions, restarting Paddock between them. Each starts from the current durable knowledge revision without the user asking for architecture/documentation updates.
6. Include dirty and untracked input changes, branch/config changes and an external edit missed by the watcher. Fingerprint reconciliation invalidates only affected knowledge and refreshes it at the next relevant gate.
7. Two workers propose knowledge deltas for successive snapshots. The older delta cannot replace newer facts or interpretations. Fact extraction, hypotheses, reviewed interpretation and owner intent remain distinguishable.
8. Fail knowledge persistence after code verification. Task completion requires its durable outbox obligation, not a synchronous semantic-model update. Do not call the map fresh or silently finish the maintenance obligation. Replay the outbox idempotently; recover internally where authorized and expose one project problem only when necessary.
9. A worker claims documentation was updated but supplies no supported delta/coverage. The completion gate rejects the claim. A supported no-semantic-change result remains possible when the actual diff warrants it.
10. An unmanaged CLI bypasses hooks. Do not claim it read/enforced knowledge. Detect its repository changes before the next managed action and label the relevant coverage honestly.

## Minimal owner work

11. Complete five routine authorized worker operations with applicable checks and safe integration. Required owner task-resolution clicks: zero. Record verified/integrated dispositions without inventing owner approval or automatically marking product milestones done.
12. Opening optional Work detail shows the actual brief, approach, difficulty estimate, recommended route, actual route when verified, selection reason and checks. Missing model verification stays unknown. The owner does not need to choose a model for each task.
13. A reversible implementation choice and recoverable technical failure stay within the authorized workflow and budget. Unapproved spend, public deployment, destructive action, scope expansion or incompatible owner constraints produces one concise decision with consequences and a recommended action. No paid/model fallback or correction loop exceeds standing authorization.
14. Multiple attempts at one blocked outcome produce one decision/problem identity, not one unread notification each. Progress and knowledge refresh create no routine unread chores. Optional Pause/Cancel remains available.

## Useful Results

15. Routine worker successes, failures, replacements, check logs, internal reviews and project knowledge updates create zero Results cards. Completion does not demand a report ID for each worker.
16. An explicitly requested useful artifact appears once. Updating it advances one logical deliverable and retains prior versions internally rather than creating duplicate cards. Optional export/keep of a work detail is explicit.
17. Migrate known operational records to execution history/archive without deleting files/IDs. Retain ambiguous and explicitly kept items; preserve versions and undo. Do not ask the owner to bulk-Close the backlog or hide live/uncertain processes.

## Engineering integrity

18. Admit five eligible managed workers in each of two projects, then queue the sixth per project. All planner/review/child/local-assist entry points share the correct project pool. No unverified account-one/stale-quota fallback; explicit global/account budgets and physical resources explain their own blockers.
19. Resource-eligible fair admission has no head-of-line or partial-resource deadlock. Managed nested spawning is disabled; split parents relinquish slots/conflicting leases. Current-checkout writes remain exclusive unless restrictions are enforced; authorized isolated workspaces and serialized checked publication preserve work.
20. Repeated Start/Resume/Approve/integration commands and crash-uncertain dispatch never duplicate model attempts or publication. Immutable artifacts, exact intents, current authority/target and applicable evidence are revalidated. System integration cannot grant broader owner authority.
21. Crash/fail every task, knowledge, merge and deliverable persistence boundary. Reconcile real effects and journals; do not fake cross-store atomicity, replay uncertain work or lose owner changes. Stop still attempts physical termination if bookkeeping storage fails.
22. Live summaries stay bounded and exclude full logs/diffs/secrets; history/detail are explicit reads with opaque phone grouping and stale-response guards. Knowledge inspection is readable on desktop/phone. Repeated keyboard actions and live updates preserve focus and drafts.
23. Migrate twice, interrupt/resume discovery and test the documented rollback on temporary data after quiescing workers, merges, repairs and knowledge writes. Newer schema cannot be down-migrated by assumption. Backend rollback retains upgraded data and reconciles publication made after the backup.

Run npm run build, npm test, npm run test:linux and applicable Flutter analyze/tests during implementation. Use temporary stores and mocked providers, with no paid test requests. Measure actual knowledge-update/render/payload costs before making performance or savings claims.

## Indexed knowledge/retrieval gates

24. Move/rename/delete responsibilities and regenerate numbered directory views. Canonical IDs remain stable; address lookup requires its directoryViewId, and old receipts use stable IDs or the retained historical view. Never resolve a bare stale number to a different responsibility. Tombstone retired stable IDs. Profiles omit irrelevant branches; reverse lookup exposes uncovered code.
25. Extract overloaded/duplicate symbols from pinned dirty/untracked snapshots, with compiler/generated-type configuration. Return the exact requested source and honest context coverage; reject wrong symbols, mixed snapshots, path escape and redacted-as-exact claims.
26. Update a neighboring contract or add/delete a dependency during a semantic write. Dependency read-set/query-digest checks detect the conflict; disjoint still-valid writes need not fail because an unrelated global revision changed.
27. A small writer omits an important side effect or claims no semantic change from unchanged signatures/passing tests. Reject unsupported claims; mechanically valid schema or model confidence is not sufficient semantic verification.
28. Overflow directory, section and source budgets. Page/split by semantic responsibility, return explicit continuation/oversize/coverage and do not silently truncate or trigger a paid/strong-model fallback.
29. Run the preregistered equal-outcome pilot against bounded conventional search, including a 15-25-change sequence and concurrent workers. Count initialization, maintenance, routing, lead/review, failed attempts, cached tokens and unknown usage before claiming savings.
30. After a starting-folder selection, offer one Create project here action when unbound. Do not create duplicate projects, execute imported scripts or ask the owner to repeat project registration for each worker.

## Argon reconciliation gates

31. Five workers complete adjacent changes while prose maintenance is delayed. Completion/outbox writes remain durable, workers release execution slots, dirty markers propagate and the coalescing documentation queue eventually refreshes them within policy. Its model turn counts within the same five-project pool, not as an uncounted sixth worker.
32. Crash between completion/outbox persistence, relay, dirty marking and interpretation commit. No maintenance obligation disappears or duplicates; gate-time source reconciliation catches missed notifications. A stale contract is delivered only with its status and exact intervening source/AST diff.
33. Change signatures repeatedly. knowledge.read/bundle materializes current snapshot-bound API facts; semantic records contain references/obligations without redundant signature prose writes. Owner intent remains protected from model patches.
34. Two distinct declaration/field patches in one section can merge when their read sets and invariant dependencies stay valid. A changed shared invariant, relevant configuration, new dependency or coupled flow invalidates dependent proposals even if individual cited function bodies are unchanged.
35. Compare transformations with matching control-flow shape but different constants/effects, reflected local names or compiler directives. General AST/CFG/DFG similarity cannot automatically certify semantic equivalence. A valid anchor also cannot certify the truth/completeness of a proposed obligation.
36. Begin with deterministic fixtures and six paired feasibility tasks. Run broader chunk tuning, 25-task and sequential-drift experiments only after useful evidence. Critical stale/wrong-symbol/contract errors fail the fixture gate; do not accept them merely because an aggregate drift percentage is below 10%.
